#0017 — Document Standard

1. Purpose

This standard defines the expected anatomy of Archivo 21 documents.

Its purpose is to ensure that documents are structured consistently enough to be understood, reviewed, maintained, compared and superseded without forcing every document into the same shape.

The standard establishes:

  • which recorded elements should normally appear in each document class;
  • which elements belong at the beginning of a document and which belong after the substantive text;
  • when footnotes or equivalent supporting notes are appropriate;
  • when a document may omit part of the standard anatomy; and
  • when the structure should be avoided altogether because it would add ceremony without adding clarity.

Consistency is a means of preserving understanding. It is not a reason to overengineer simple work.

2. Scope

This standard applies to institutional documents created, adopted or maintained by Archivo 21, including:

  • constitutional documents;
  • governance documents;
  • policies;
  • standards;
  • procedures;
  • registers;
  • technical specifications;
  • research reports;
  • decision records; and
  • operational guidance.

It does not require every ordinary note, checklist, message, draft fragment, capture record or working file to adopt a formal institutional anatomy.

3. Definitions

3.1 Recorded element

A recorded element is a category of information that a document should preserve, whether as a heading, metadata field, note, register entry or linked record.

Recorded elements include:

  • Purpose
  • Scope
  • Definitions
  • Principles
  • Requirements
  • Exceptions
  • Responsibilities
  • Procedures
  • Review history
  • Status
  • Version
  • Effective date
  • Superseded by
  • References

A recorded element does not always require a visible section heading. Its form should follow the needs of the document.

3.2 Lead element

A lead element appears before the main substantive body because the reader needs it in order to interpret what follows.

3.3 Follow-up element

A follow-up element appears after the main substantive body because it records history, authority, relationships, evidence or maintenance information that supports the document without needing to interrupt its argument.

3.4 Footnote

A footnote is a subordinate note attached to a specific statement.

For the purposes of this standard, endnotes, linked annotations and equivalent repository notes may perform the same function where the publication format makes conventional footnotes impractical.

3.5 Document class

A document class is the functional category that determines which recorded elements are required, recommended or unnecessary.

3.6 Lifecycle status

Lifecycle status records where an institutional document stands as an instrument or record.

The approved terms are:

  • Draft — incomplete working text with no institutional authority;
  • Proposed — complete enough for a decision but not yet adopted;
  • In Review — undergoing an identified review;
  • Adopted — approved, but not necessarily yet effective;
  • Active — currently operative or maintained;
  • Superseded — replaced by an identified later version or document;
  • Withdrawn — deliberately removed from consideration or operation without being replaced; and
  • Archived — retained for history and no longer maintained.

Lifecycle status does not measure evidential certainty.

3.7 Publication state

Publication state records who may access a document. Approved descriptions include Internal, Restricted, Public draft, and Public.

Publication is not a lifecycle status. A draft can be public, and an active record can remain internal or restricted.

Daily and session decision logs are internal by default. Their publication requires an explicit release decision or a separately prepared public account.

3.8 Canonical location

A canonical location is the designated authoritative copy of a document.

“Canonical” describes authority and location, not lifecycle status or certainty. A canonical copy may still be a draft.

Rendered website pages are publication copies. Unless explicitly designated otherwise, the corresponding Markdown file in the responsible repository remains authoritative.

3.9 Document identifier

A document identifier is the permanent institution-wide number assigned through the Institutional Document Register.

The identifier records documentary sequence, not importance, authority, topic or project relationship.

4. Core rule

Every formal Archivo 21 document should have a predefined anatomy appropriate to its function.

The anatomy should be selected from this standard before drafting begins wherever practical.

A document should include every recorded element needed to understand:

  1. what the document is;
  2. what it applies to;
  3. what it requires, establishes or records;
  4. what limits or exceptions affect it;
  5. what authority and status it holds; and
  6. how it relates to earlier, later or supporting records.

A document should not include headings merely to demonstrate compliance with this standard.

An empty, repetitive or self-evident heading should be omitted.

5. Universal recorded elements

Every formal institutional document should record the following somewhere in the document or its authoritative register entry:

5.1 Title

The title should identify the subject and function of the document without requiring the reader to open it.

5.2 Status

The document should record lifecycle status separately from publication state and canonical location.

Only an approved lifecycle term from section 3.6 should be used in the status field.

5.3 Version

The current version should be recorded when the document is expected to change, be reviewed or coexist with earlier versions.

A document that is immutable by design may instead record a date or event identifier.

Versions of the same continuing instrument retain the same institutional document identifier.

5.4 Authority or ownership

The responsible institutional body, role or project should be identifiable.

This may be recorded directly in the document or through the document register.

5.5 Relationship to other records

Where applicable, the document should identify documents that it replaces, depends upon, implements or is superseded by.

5.6 Date

A creation, approval, effective or publication date should be recorded according to the document's function.

Not every document requires all four dates.

5.7 Identifier

Every substantial institution-wide document should carry its Institutional Document Register number once assigned.

Source, accession, experiment and project identifiers remain distinct and must not be converted into institutional document numbers.

5.8 Publication state and canonical path

Every formal document should identify its publication state and canonical path directly or through the authoritative register.

The public website should link readers to a readable webpage and, where useful, from that webpage to the canonical repository source.

6. Placement of recorded elements

6.1 Lead elements

The following elements are best suited to the beginning of a document:

  • Title
  • Status
  • Version
  • Purpose
  • Scope
  • Definitions required for interpretation
  • Authority, where the reader must know it before relying on the text
  • Effective date, where obligations begin on a particular date

These elements answer the reader's first questions: what is this, why does it exist, and where does it apply?

6.2 Main-body elements

The following elements normally belong in the substantive body:

  • Principles
  • Requirements
  • Responsibilities
  • Procedures
  • Criteria
  • Controls
  • Exceptions that materially affect application
  • Examples needed to interpret the rule

These elements contain the document's operative meaning.

6.3 Follow-up elements

The following elements are best suited to the end of a document or its associated register record:

  • Review history
  • Approval history
  • Version history
  • Supersedes
  • Superseded by
  • References
  • Related documents
  • Appendices
  • Non-operative drafting notes
  • Contact or maintenance information

These elements help maintain and verify the document without delaying access to its substantive content.

6.4 Elements that may move

Some elements may appear in more than one position:

  • A short exception may appear beside the rule it limits.
  • A complex exceptions regime may require its own later section.
  • Essential definitions belong near the front.
  • Specialist or rarely used definitions may belong in a glossary or appendix.
  • A small number of references may appear inline.
  • A substantial reference apparatus belongs at the end.

Placement should follow reader need rather than mechanical uniformity.

7. Document classes and expected anatomy

7.1 Constitutional documents

Examples include Vision, Mission, Values and Success Criteria.

Normally required:

  • Title
  • Status
  • Version or approval date
  • Purpose, where the title alone does not make the function obvious
  • Principles, commitments or criteria
  • Relationship to other constitutional documents
  • Review or approval history

Normally optional:

  • Scope
  • Definitions
  • Exceptions
  • References
  • Footnotes

Constitutional documents should remain readable as statements of institutional identity.

They should not be burdened with policy machinery unless that machinery is essential to their meaning.

7.2 Governance documents

Examples include authority frameworks, decision rules, committee terms and institutional registers.

Normally required:

  • Purpose
  • Scope
  • Definitions
  • Authority
  • Responsibilities
  • Decision or control rules
  • Exceptions or escalation routes
  • Status
  • Version
  • Review history
  • Related documents

Governance documents should make responsibility and authority unambiguous.

7.3 Policies

Examples include the Acquisition Policy.

Normally required:

  • Purpose
  • Scope
  • Definitions where necessary
  • Principles
  • Operative policy statements
  • Responsibilities where applicable
  • Exceptions, discretion or escalation
  • Status
  • Version
  • Review history
  • Related documents and references where needed

A policy explains what the institution intends, permits, requires or refuses.

Detailed step-by-step instructions should normally be placed in a procedure rather than embedded in the policy.

7.4 Standards

Examples include this Document Standard and future technical or documentation standards.

Normally required:

  • Purpose
  • Scope
  • Definitions
  • Normative requirements
  • Classification or conformance rules
  • Permitted exceptions
  • Examples
  • Status
  • Version
  • Review history
  • References where the standard depends on external or internal authorities

Standards should distinguish clearly between:

  • mandatory requirements;
  • recommendations;
  • permissions; and
  • examples.

7.5 Procedures

Normally required:

  • Purpose
  • Scope
  • Preconditions
  • Responsibilities
  • Ordered steps
  • Decision points
  • Exceptions and failure handling
  • Required outputs or records
  • Version
  • Effective date
  • Related policy or standard

Procedures should optimise for use during action.

Background discussion should be brief or linked elsewhere.

7.6 Registers

Examples include the future Institutional Document Register.

Normally required:

  • Purpose
  • Scope
  • Field definitions
  • Entry rules
  • Responsible maintainer
  • Status
  • Version or last-updated date

Individual register entries do not require their own Purpose, Scope or Review History headings unless an entry becomes a document in its own right.

7.7 Technical specifications

Normally required:

  • Purpose
  • Scope
  • Definitions
  • Assumptions and dependencies
  • Requirements
  • Constraints
  • Interfaces or formats
  • Validation or acceptance criteria
  • Known exceptions
  • Version
  • References

Technical specifications may use tables, schemas, code blocks or diagrams in place of prose headings where those forms communicate more precisely.

7.8 Research reports

Normally required:

  • Research purpose or question
  • Scope
  • Sources or evidence
  • Method
  • Findings
  • Uncertainty and limitations
  • Conclusions
  • Status or research state
  • Version or date
  • References

Research reports should separate evidence, interpretation and speculation.

7.9 Decision records

Normally required:

  • Decision
  • Date
  • Context
  • Rationale
  • Consequences or follow-up
  • Status
  • Related records

A decision record should be brief when the decision is simple.

It should not imitate a policy merely because it may later influence one.

7.10 Operational guidance

Normally required:

  • Purpose or task
  • Intended user
  • Instructions
  • Warnings or limits
  • Related procedure or standard where relevant
  • Version or last-reviewed date when the guidance can become outdated

Operational guidance should privilege usability over constitutional formality.

8. Footnotes and supporting notes

8.1 When footnotes are appropriate

Footnotes or equivalent notes are appropriate when they:

  • identify a source for a specific factual claim;
  • preserve a narrow qualification without interrupting the main text;
  • explain a historical term, superseded name or unusual technical detail;
  • distinguish an example from a binding requirement; or
  • record provenance that belongs to a particular sentence or item.

8.2 When footnotes should be avoided

Footnotes should not be used to:

  • hide a substantive rule;
  • contain an exception that materially changes the main text;
  • carry essential definitions;
  • preserve lengthy drafting discussions;
  • create a parallel document underneath the document; or
  • compensate for unclear structure.

A reader should not need to inspect every footnote to know what the document requires.

8.3 Documents that normally benefit from footnotes

Footnotes are most useful in:

  • research reports;
  • historical records;
  • evidential summaries;
  • technical analysis;
  • annotated transcriptions; and
  • constitutional or policy documents containing claims tied to particular sources.

8.4 Documents that normally should avoid footnotes

Footnotes are normally unnecessary in:

  • short procedures;
  • checklists;
  • registers;
  • quick-reference guidance;
  • simple decision records; and
  • concise constitutional statements that do not rely on external claims.

9. Exceptions and proportionality

9.1 Rule of thumb

Use the formal anatomy when omission would make the document harder to interpret, apply, review, maintain or supersede.

Avoid the formal anatomy when the headings would be longer or more complex than the useful content they organise.

9.2 Indicators that formal structure is appropriate

A document should normally use the structured anatomy when one or more of the following apply:

  • it establishes an institutional rule;
  • it applies to more than one project or contributor;
  • it authorises, prohibits or constrains action;
  • it is expected to remain in force;
  • it may be revised or superseded;
  • ambiguity could cause loss, inconsistency or harm;
  • future readers will need to understand its authority or history; or
  • it depends on definitions, exceptions or relationships with other documents.

9.3 Indicators that formal structure should be reduced or avoided

A lighter structure is normally appropriate when the document is:

  • a temporary working note;
  • a single-purpose checklist;
  • a brief capture record;
  • a file inventory entry;
  • a short explanatory note attached to one object;
  • a transient planning fragment;
  • a simple factual record with no operative rule; or
  • a message whose function is exhausted once acted upon.

Such documents may still require a title, date, identifier or provenance field.

They do not need ceremonial headings that add no useful distinction.

9.4 Exemption rule

A document may depart from the expected anatomy where:

  1. the document's purpose remains clear;
  2. no material rule, limit or status is concealed;
  3. the departure reduces burden without reducing reliability;
  4. the document can still be maintained and interpreted later; and
  5. the reason for the departure would be apparent to a competent future reader or recorded where it would not be apparent.

10. Existing documents and exemptions

The following existing documents illustrate proportionate departure from the full anatomy.

10.1 Vision

The Vision document is exempt from a separate Scope, Definitions and Exceptions structure.

Its function is aspirational and institution-wide.

Adding those headings would fragment a concise statement whose meaning depends on continuity of voice rather than procedural precision.

It should still retain status, approval history and relationship to the wider constitutional set through metadata or the document register.

10.2 Mission

The Mission document is exempt from a detailed Responsibilities or Exceptions section.

It defines what Archivo 21 exists to do rather than assigning operational duties.

A short Purpose heading may be redundant where the mission statement itself performs that function.

10.3 Values

The Values document is exempt from a conventional Purpose, Scope and References apparatus within the visible body.

The values are intended to be read directly as institutional commitments.

Its revised and superseded states should instead be preserved through version history and the document register.

10.4 Success Criteria

The Success Criteria document benefits from structured thematic sections but does not require a conventional Definitions section unless specialised terms are introduced.

Its criteria are interpretive and institutional rather than a technical conformance test.

Forcing each criterion into Requirement, Exception and Responsibility subheadings would overstate its procedural function.

10.5 Acquisition Policy

The Acquisition Policy is not exempt from the policy anatomy.

It already contains Purpose, Scope, principles, discretion, limits and review provisions.

On formal adoption, it should additionally receive complete metadata, status, version, approval history and related-document references.

10.6 Daily decision log

A daily decision log is exempt from full policy or standard anatomy.

Its entries should record the decision, context, rationale and consequences, but the log itself need not repeat Purpose and Scope for every entry.

The log may be governed by a separate template.

10.7 Simple inventories and capture records

A list of files, screenshots, recordings or discovered references is exempt where it merely records what exists.

It should record enough provenance and identification to remain useful, but it does not need Principles, Exceptions or Review History unless the inventory itself makes evaluative or governing decisions.

11. Metadata and visible headings

A recorded element may be satisfied through:

  • a visible section;
  • a document header;
  • front matter;
  • a register entry;
  • repository metadata;
  • a version-control record; or
  • a linked decision record.

The chosen location must be authoritative and reasonably discoverable.

Information should not be duplicated across several locations unless duplication improves resilience or use.

Where duplicated records conflict, the designated authoritative source must prevail.

11.1 Compact metadata pattern

The following fields form the normal institutional pattern:

Identifier:
Document class:
Lifecycle status:
Version:
Created:
Last reviewed:
Adopted:
Effective:
Publication state:
Authority:
Canonical path:
Supersedes:
Related records:

The Institutional Document Register may satisfy fields that would make a short document unnecessarily heavy, provided the relationship is unambiguous and discoverable.

12. Identifiers, numbering and chronology

12.1 Initial reconstruction

Placeholder numbers used before adoption of the Institutional Document Register may be reassigned once to reconstruct the institution's documentary chronology.

The reconstruction must:

  • preserve the former filename or working number;
  • record the source and confidence supporting the order;
  • compare competing versions before selecting the current text; and
  • retain superseded and defective compilations as institutional memory.

12.2 Stable numbering

After the initial chronology is adopted:

  • numbers are assigned in chronological order from the next available value;
  • assigned numbers are permanent and must not be reused;
  • a revised or superseded version keeps the same number;
  • renaming or moving a document does not change its number;
  • gaps remain gaps rather than triggering renumbering; and
  • project, experiment, source, accession and contributor identifiers remain in their own namespaces.

The register is authoritative when a filename, title or earlier note conflicts with the adopted number.

12.3 Uncertain chronology

Where exact order cannot be established, the register should record the uncertainty and the evidence used for the adopted sequence.

An uncertain date must not be made artificially precise.

13. Drafting rules

Writers should:

  1. identify the document class before drafting;
  2. select the expected anatomy from this standard;
  3. remove headings that would be empty or self-evident;
  4. add missing elements where their absence would create ambiguity;
  5. distinguish operative text from discussion, examples and history;
  6. place maintenance information after the substantive text where practical;
  7. use footnotes only for genuinely subordinate information; and
  8. record any significant departure from the standard where the reason would not otherwise be clear.

14. Review rules

Review of a document's anatomy should ask:

  • Can a new reader identify the document's purpose and authority?
  • Is the scope clear enough to prevent accidental overreach?
  • Are essential terms defined before they are used?
  • Can binding requirements be distinguished from examples or commentary?
  • Are exceptions visible where they affect action?
  • Can the document's status, version and history be established?
  • Has structure improved understanding, or merely increased ceremony?

A document should not fail review merely because it omits a heading listed in this standard.

It should fail where the omitted information is necessary.

15. Conformance

A document conforms to this standard when:

  • its class has been identified;
  • all necessary recorded elements are present;
  • those elements are placed where readers can use them;
  • omitted elements are genuinely unnecessary;
  • the document remains proportionate to its purpose; and
  • its status and history can be established.

Conformance is based on preserved function, not visual uniformity.

16. Exceptions to this standard

Archivo 21 governance may authorise departure from this standard where an unusual format, preservation constraint, inherited document or external requirement makes conformance impractical or harmful.

The departure should preserve as much of the document's identity, authority, meaning and history as circumstances allow.

Inherited or externally authored material should not be rewritten merely to resemble Archivo 21 documentation.

Where necessary, Archivo 21 may attach a wrapper record containing the missing metadata or contextual elements.

17. Publication and web representation

When a document is made public:

  • the public route must be a readable webpage rather than a raw Markdown or plain-text destination;
  • Markdown syntax must be rendered as headings, lists, tables, links, code and quotations;
  • the page must identify lifecycle status, version and canonical source;
  • internal website links must resolve to webpages;
  • superseded public versions should remain discoverable from the current page or version record; and
  • restricted or internal source material must not be released merely because it informed a public summary.

The website may generate or copy rendered publication pages from canonical repositories. Those pages do not silently become additional authoritative records.

18. Change control, recovery and maintenance

This standard should be reviewed when:

  • repeated exemptions reveal that a document class is poorly defined;
  • contributors cannot determine which anatomy applies;
  • new document classes become common;
  • repository tooling changes where metadata is stored;
  • required headings produce repeated unnecessary work; or
  • missing elements repeatedly cause confusion or loss.

Changes to the standard should preserve the principle that structure exists to save future effort, not manufacture present burden.

Changes must also follow #0008 Change Documentation Policy. Every repository or configuration change begins from an identified state and must preserve a complete, recoverable pre-change checkpoint for at least 28 days.
